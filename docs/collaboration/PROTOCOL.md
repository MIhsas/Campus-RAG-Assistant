# Astra 与 Mimo 的协作协议

建立日期：2026-09-12。

## 1 职责与交接

Astra 负责需求拆分、方案决策、任务发布、审查和验收。Mimo 在用户的 VS Code / Claude Code 中执行具体任务，提交文件和真实验证证据。用户负责将启动指令送入对应会话，并在 Mimo 交付后通知 Astra。

任务书写入项目表示“已发布”，不表示已向外部会话发送或 Mimo 已启动。当前未建立两个会话间的自动通信，也未建立自动监控；用户通知后 Astra 才进行本轮审查。

共享同一工作目录时，Mimo 直接写指定成果目录，不必压缩上传。若在另一台电脑或目录执行，交付文件及补丁，同时说明环境差异；不能只提供截图或聊天总结代替实际成果。

## 2 单任务状态

状态顺序：已发布 → 执行中 → 待验收 → 验收通过，或待验收 → 退回修改 → 待验收。确有外部依赖时可为受阻。

`STATUS.md` 由 Astra 维护。Mimo 在自身 `submission.json` 中申报 ready_for_review、partial 或 blocked，不改任务状态表，不写 accepted。Astra 没有验收通过结论时，下一任务没有执行授权。

一次只发布一个可执行任务。路线图中的后续阶段仅用于说明方向，不是批量执行指令。返工沿用任务 ID、增加修订号；Astra 明确验收通过后才发布下一个 ID。

## 3 文件归属

- `tasks/`：Astra 发布任务书，包含范围、路径、步骤与验收条件。
- `submissions/Txxx/`：Mimo 的成果、变更清单和验证记录。
- `reviews/`：Astra 的审查结果，首次使用 `Txxx-R1.md`，后续递增。
- `STATUS.md`：当前任务与结论入口，只由 Astra 更新。
- `docs/01` 至 `docs/04`：现有系统方案，Mimo 提出变更建议但不自行重写。
- `step2_code/`：后续获批任务的代码目录，当前 T001 不允许修改。

## 4 每次交付必须包含

完成报告说明做了什么、修改哪些文件、验证了什么、未完成什么和已知限制；命令记录包含工作目录、命令、退出码及相关输出摘要。真实日志需要脱敏。文件清单应完整覆盖本任务新增和修改的文件。

有代码的任务必须交付可复现运行方式及针对业务行为的测试；不能只提交“全部通过”的文字。无代码的盘点任务不要求人为增加测试或安装环境。若被外部条件阻塞，提交已完成部分和准确阻塞原因，不以模型推测补齐。

## 5 Astra 的验收规则

审查四项：是否满足任务要求；设计是否符合现有约束；证据是否可复查；是否引入越界修改或风险。有代码时读取变更并独立运行必要验证，不能仅凭执行模型的结论验收。

结论只能明确为“验收通过”“退回修改”或“受阻”。存在影响下一任务的必修问题时不以“基本通过”放行；可选建议可以记录而不阻止交付。验收记录列出检查项、证据、问题及下一步授权。

## 6 后续阶段方向

T001 环境与资料基线 → 校园语料与问题集 → 离线解析/检索基线 → RAG 问答与引用 → 前后台与办事功能 → 受限 Agent → 实验与交付。实际任务 ID 和拆分由前一任务验收结果决定，不能预先连续执行。

Windows 是已确认开发主机；是否使用 WSL2 尚未由用户明确选择。不得因系统方案推荐 WSL2 就自行安装。RAGFlow 只参考；TinyAgent 具体仓库仍需在实际集成任务前确定。

## 7 用户确认的加速节奏（2026-09-21）

用户要求后续任务加速，减少冗余安全及边界测试。将可连续交付的算法、API、页面、评测适配合并安排；验收集中于功能主路径、数据/指标正确性、已复现问题和一次必要回归。没有新失败或新改动不重复测试。普通措辞、文档哈希遗漏和低影响边界作为非阻断整理项，不单独循环返工；影响结果可信度、主功能不可用或用户数据的实质问题仍须修复。测试条数不是交付目标。
