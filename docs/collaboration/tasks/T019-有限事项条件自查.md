# T019 有限事项条件自查

日期：2026-09-27；task_revision=v1。Astra 发布，MiMo v2.6 Pro 执行。前置 T018-R2 通过。

## 目标与范围

落实 docs/04 的有限规则自查：只做一个“转专业条件自查（合成演示）”，让用户填写必要条件，查看逐项满足/不满足/待核实、原文依据与待确认信息。是个人自查演示，不受理申请、不代表学校审核结果。无需模型或通用规则引擎，不新增账号、数据库、Agent、语音或前端框架。

## 实施

1. 使用现有 parse-corpus/sample.txt 第五条作为唯一合成规则依据，原语料、manifest、gold 不变。独立规则配置显式绑定文档/块/跨度/哈希，包含规则版本；由工厂显式注入，普通未配置服务不自动启用合成规则。可复用 procedures 的引用与筛选核查，但不复制第二套准入逻辑。
2. 规则仅对应原文四项：是否入学后第一学年末、在读期间是否无违纪记录、第一学年加权平均成绩排名是否前30%、是否通过接收学院考核。全部允许“不确定/未填写”。排名采用用户自报“是否在前30%”三态，不凭未说明的并列/取整规则自行换算。字段、肯否方向与原文一致；未参加考核为待核实，与明确未通过区分。不收姓名、学号、违纪详情。
3. 后端显式确定性判断，禁止 eval 或 LLM 生成规则。每项返回用户填报、状态、解释与有效引用。必要输入未知不得算满足；任一明确不满足总结为“存在未满足项”；无不满足但有未知为“仍有待核实项”；全满足为“按自填信息满足本演示列出的条件”，仍需学校审核，不输出录取/批准/申请成功。依据不通过准入或缺失/哈希变化时总结为“依据不足，无法完成自查”，不利用失效原文算通过。
4. 提供规则信息与执行自查 API（可用 /api/v1/self-check/...，在报告说明选择）。复用四项 filters。引用链接由服务器绑定原文，不接收客户端拼接引用。未配置有明确不可用响应。用户资料仅本次请求处理，不写报告、日志或 localStorage。
5. 提供 /self-check 页面：首页入口→筛选→三态表单→手动自查→逐项结果及原文跳转→修改重查/清空。结果展示已提交输入及条件快照，用户改表单不悄悄改旧结果；失败明确未生成新结果；资料不足与个人条件不满足分别表达。只在点击后执行，不自动调用模型或保存待办。首页增加第六入口，并在统一 demo 中显式注入规则配置。可从 ask 的转专业关键词提供相关自查入口（可选，不作为验收必需）。
6. 更新 Windows 演示说明，给出全满足、缺考核信息、一个不满足、依据被筛除四个可操作场景。全部明确合成资料、确定性规则，不能宣传真实校园资格准确率。
