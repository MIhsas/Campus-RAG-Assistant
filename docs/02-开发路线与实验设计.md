# 开发路线与实验设计

初始规划日期：2026-09-10；v1.1 修订日期：2026-09-12。依赖：[系统方案](./01-系统方案.md)、[资料与 GitHub 调研](./03-资料与GitHub调研.md)、[前台体验与 Agent 方案](./04-前台体验与Agent方案.md)。本文件是可执行的阶段规划，不代表相关功能已实现。

## 1 从现在到答辩的主线

2026-09-12 协作更新：四川农业大学与校内公开网站来源已确认，资料由用户后续提供；导师不限定方法，后端选用路线 A。下文排期中的学校/路线确认事项已解决，具体语料收集仍未完成，其他阶段不因此自动视为完成。

建议按“真实语料 → 检索基线 → 最小问答闭环 → 双端系统 → 场景优化 → 对照实验 → 稳定交付”推进。不要先花数周做登录页、热搜榜和监控大屏，再发现核心文档解析错误。

v1.1 加入用户可见功能后，按 16 周约 245—375 小时、每周约 15—24 小时估算，较原计划净增约 55—85 小时。该数字是单人预算，需结合编程基础修订；时间不足按前台方案第 8 节削减扩展和 Agent 自由编排，保留固定向导、语音、清单及核心实验。两套后端并行学习会增加风险，优先采用熟悉技术。

原报告将开发安排在 2026 年 5—12 月，但当前目录只有报告，不能假设此前已完成代码。本计划从 2026 年 9 月重新建立可验证里程碑。

### 2.1 前两周具体工作

| 次序 | 任务 | 输入 | 输出 | 完成判断 |

## 3 论文研究问题

RQ1：相同生成模型下，BM25 + BGE + RRF 是否改善校园专有名词、数字和口语问题的检索质量？

RQ2：结构化条款/表格切分是否比固定长度切分更好地保留条件、例外与跨行信息？

RQ3：加入适用对象与政策有效期约束后，旧政策误用和跨年级误答是否减少？它是否增加了不必要的澄清或拒答？

RQ4：reranker 与条件化查询改写增加的准确性收益，能否补偿额外时延和调用成本？

RQ1—RQ3 是主线。时间不足时 RQ4 只完成一个增强项或作为展望，避免为了“功能齐全”而做无法解释的组合实验。新增语音、资格自查和办事任务属于系统与体验评价，单独报告，不把 Agent 带来的表现变化混入 RAG 消融。

## 4 数据集建设

### 4.1 建议规模与覆盖

建议累计 240 个评测实例，开发集 80、测试集 160；若实际材料不足，明确缩小规模并在论文中报告限制，不能编造本校政策凑数。

| 主类别 | 建议实例数 | 典型挑战 |
|---|---:|---|
| 单条款事实 | 50 | 条件、材料、次数、办理部门 |
| 专有名词与口语 | 40 | 课程代码、简称、同义表达 |
| 多条款或表格 | 35 | 同时覆盖资格、材料、例外 |
| 时间与适用范围 | 40 | 旧版、新版、不同年级/专业 |
| 多轮指代 | 25 | “那需要什么材料”“我说的是补考” |
| 信息不足、无答案或冲突 | 35 | 需要追问、缺少依据、政策矛盾 |
| 提示注入与越界请求 | 15 | 诱导编造、忽略证据、获取他人信息 |
| 合计 | 240 | 每题一个主类别，可有多个辅助标签 |

多轮实例按整个对话分组，不将前后轮拆入不同集合。注入与权限题另外进入安全回归集；安全结论不能只靠这 15 题。

### 4.2 标注字段

question_id、question、history、confirmed_scope、as_of_date、expected_action、reference_answer_points、gold_document_versions、gold_evidence_spans、relevance_grade、category、difficulty、annotator、split。

expected_action 区分回答、澄清、拒答、冲突、越界。澄清题标出缺失字段；冲突题标出互相冲突的版本；无答案题明确是当前冻结语料没有依据，而非世界上不存在答案。

金标准优先标原文条款或跨度，不绑定某种切分产生的 chunk_id。多证据题注明哪些证据是全部必需，哪些是等价替代来源。这样才能判断“召回一条”与“足够作答”的差别。

### 4.3 防止评测泄漏

同义改写、同一条款派生题、同一对话的样本按组切分。政策版本冲突题按同一政策家族分组。知识文档在问答时可检索是 RAG 任务的正常设置，但测试问题、金答案、人工纠错标准答案不能加入检索语料或提示词示例。

仅在开发集选参数和阈值，测试集冻结后不因分数低而删题。若修订金标准，保存版本和理由，所有比较系统重新运行。模型可协助提出问题初稿，但人工必须对照原文确认；保留人工自然提问，避免题集全是与原文高度相似的生成问句。

## 5 对照与消融实验

### 5.1 主实验矩阵

| 编号 | 配置 | 目的 |
|---|---|---|
| E0 | 同一 LLM，不提供文档上下文 | 观察领域知识缺失与无依据回答；不是完整系统的公平替代 |
| E1 | BM25 + 固定切分 + 同一 LLM | 稀疏检索基线 |
| E2 | BGE + 固定切分 + 同一 LLM | 稠密检索基线 |
| E3 | BM25 + BGE + RRF + 固定切分 | 隔离混合召回收益 |
| E4 | E3 + 结构化切分 | 隔离条款与表格结构收益 |
| E5 | E4 + 时间/适用范围决策 | 评价场景约束与回答动作 |
| E6 可选 | E5 + reranker | 评价精排增益与时延 |
| E7 可选 | E5 + 条件化查询改写 | 单独评价改写，避免与精排混淆 |

如果 E6、E7 都有效，再增加 E8 为二者组合，不从组合结果倒推单项贡献。所有系统保持相同模型、输出长度、温度、原始语料快照和上下文预算。E4 引入父级扩展时需保持上下文 token 上限，或额外报告去掉父级扩展的实验，避免切分与上下文长度混淆。

E5 的评价必须同时给出可回答题正确率、拒答题表现、澄清正确性和回答覆盖率，不能把多拒答导致的“少犯错”当作全面提升。

### 5.2 调参范围

先在开发集小范围试验：切片目标长度 256/384 tokens、重叠 32/64；双路召回各 10/20/40；生成证据 3/5/8；RRF 常数固定 60 作为起点。长度还需给标题前缀留空间。

避免所有参数笛卡尔积穷举。先固定模型与切分比较检索，再固定检索比较切分，最后比较增强项。保留没有改善的结果，它们同样能解释技术取舍。

### 5.3 指标定义

| 维度 | 指标 | 定义与注意事项 |
|---|---|---|
| 检索 | Evidence Recall@K | Top-K 覆盖的必要金标准证据单元数 / 必要证据总数；在可回答题上宏平均 |
| 检索 | Hit@K | 是否至少命中一条相关证据；不要与 Recall@K 混称 |
| 检索 | MRR@K | 第一条相关结果排名倒数，无命中为 0 |
| 检索 | nDCG@K | 使用人工 0/1/2 相关等级；需明确去重与证据映射规则 |
| 作答 | 要点正确率 | 正确覆盖的标准要点占比；遗漏与错误分别记录 |
| 作答 | 完整正确率 | 结论、条件、数字和出处均正确的实例比例 |
| 引用 | 引用支持率 | 经核验能支持关联主张的引用关系 / 全部引用关系 |
| 引用 | 关键主张覆盖率 | 有正确证据支持的关键事实主张 / 全部关键事实主张 |
| 决策 | 拒答 precision/recall | 在应拒答与不应拒答标签下计算，澄清和技术错误单列 |
| 决策 | 澄清正确率 | 应澄清实例中问对缺失条件的比例；同时报过度澄清率 |
| 政策 | 过期或错范围回答率 | 时间/范围子集内使用不适用政策作答的实例比例 |
| 服务 | p50/p95 端到端时延 | 从客户端发起到完整有效答复；冷启动与预热分开 |
| 服务 | 阶段耗时、错误率 | 分解改写、嵌入、召回、重排、生成；区分 429 与 5xx |
| 成本 | 每问 token 与调用数 | 包括改写、生成、重试；评测模型成本单独统计 |

同一条款被多个重叠切片命中只计一次证据覆盖。无答案题不参与需要非空 gold 的检索 Recall 分母。纯检索指标与最终答案指标分别报告，不能用 Recall@5 代替回答正确率。

Ragas 可辅助评估答案是否被检索上下文支持，但“忠实于上下文”不代表上下文一定最新或适用于这个学生。[官方 Faithfulness 定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)。人工金标准与政策范围评价仍然必需。

### 5.4 人工评价与不确定性

建议你和一名同学独立盲评至少 50 个共同样本，隐藏系统配置标签并随机排序；记录分歧，协商后保留最终标签。评分表给出例子，避免“看起来不错”的主观评分。报告原始一致率，可进一步计算 Cohen's kappa。

检索固定配置应尽量确定性；生成式主结果可重复 3 次，保存每次响应与均值/波动。使用按问题组的 paired bootstrap 估计差值置信区间；题量小或区间跨 0 时，不写“显著提升”。自动裁判记录模型与提示词版本，并抽检其判断。

## 6 拟定验收目标

以下数值是开发目标，不是已经测得的结果。M1 获取基线后修订目标并记录原因，最终论文必须公开实际成绩。

| 项目 | 初始目标 | 限定条件 |
|---|---|---|
| 数据质量 | 所有发布文件有出处与适用信息，未知项明确标记 | 人工审核记录可查 |
| 检索 | 可回答题 Evidence Recall@5 ≥ 0.85 | 采用本文金标准定义和冻结测试集 |
| 完整正确率 | 可回答题 ≥ 0.80 | 人工评分，包含关键条件与出处 |
| 引用支持率 | ≥ 0.95 | 同时报关键主张覆盖率，避免少引用刷分 |
| 拒答 | precision、recall 均争取 ≥ 0.85 | 固定标签、单独统计澄清和故障 |
| 时间/范围 | 比 E4 降低不适用政策回答率 | 报具体样本数、差值与不确定性 |
| 本地检索 | 预热后 p95 ≤ 1 秒 | 约 1 万切片、记录 CPU/RAM、默认不含模型重排与生成 |
| 完整答复 | 单用户 p95 争取 ≤ 15 秒 | 记录模型、网络和输出长度；未达标也如实报告 |
| 可靠性 | 文档发布失败不破坏现行索引 | 故障注入与回滚记录 |
| 权限 | 预设对象级越权用例全部被阻止 | 不可外推为“系统绝对安全” |

压力测试分两层：使用模型桩测试 1/5/10/20 个并发客户端下的应用行为；使用真实 API 做受预算控制的低并发测试。模型桩结果不能宣称为真实大模型吞吐量，更不能据此写“承载全校高并发”。记录吞吐、等待队列、拒绝率、失败率和资源使用。

## 7 测试策略

v1.1 追加前台方案第 6 节的九项验收、30 个办事任务以及 30—50 段自愿采集语音测试。Agent 与固定流程使用同一工具与证据比较；如未实际接入框架，只报告固定工作流结果和可行性分析。新增测试集与原 240 个 RAG 实例分开管理。

有意义的单元测试集中在：RRF 排名合并、中文术语与数字保留、切分边界、版本生效条件、引用 ID 验证和权限判断。不要为每个简单取值函数堆测试数量。

集成测试覆盖：上传到发布、索引原子切换、撤回即时生效、问答入库、会话隔离、模型超时降级、幂等重试。端到端测试覆盖小程序提问、追问、证据查看、收藏、反馈以及管理员处理反馈。

必须手工检查的代表性情况：旧通知日期更晚但不适用于当前年级；表格有跨行表头；文件有“除……外”；用户中途换专业；原文件已撤回但历史答案仍有链接；模型在文本中伪造引用 ID；文档包含提示注入语句；两次上传同一文件；建索引时进程退出。

## 8 环境与资源预算

开发环境建议 Windows 11 + WSL2/Linux 容器。16 GB 内存可作为轻量开发的起点，32 GB 更便于同时运行 IDE、数据库、嵌入模型和解析任务；这不是已测得最低配置。先检查现有机器，不为计划预先购买 GPU。

CPU 先跑 BGE 基线，批量解析离线完成；重排或复杂 OCR 过慢时降低候选量、减少并发或只做离线实验。云生成 API 可避免本地大模型部署，但需要网络与调用预算。

向量内存可粗估为 N × D × 4 字节。以 1 万条、768 维 float32 为例，纯向量约 30.7 MB，另有模型权重、文本、Python 对象、数据库和索引元数据，不能据此推算总内存仅几十 MB。

API 预算使用公式：输入 tokens × 输入单价 + 输出 tokens × 输出单价 + 改写/裁判/重试费用。先用 50 道开发题估计平均消耗，再估算完整矩阵；为重试留 20% 余量。价格按执行当天提供商页面计算，本规划不固定价格或假定旧模型仍可用。[DeepSeek 官方模型与定价](https://api-docs.deepseek.com/quick_start/pricing/)

建议设本地预算上限和手动运行开关，避免实验脚本无界重试。提交仓库时只放密钥样例，不放真实凭据。

原始授权材料、模型权重、生成索引、含个人信息日志和密钥不直接提交到公开仓库。可公开的数据才进入版本控制；大文件保存哈希与获取说明。B 路线将 backend 明确拆成 business-service 和 rag-service。

每次合作只推进一个可验收任务。任务应包含：目标、输入、受影响模块、验收用例和本次不扩展的范围。完成后更新进度记录：做了什么、验证了什么、遗留什么、下一步什么。技术选择变化写简短决策记录并同步方案，避免下一次对话重新猜架构。

建议后续任务顺序：

1. M0：确认学校与材料，形成来源清单和 30 道人工问题。
2. M1：构建可重复运行的离线解析与检索基线，不调用付费生成模型也能验收。
3. M2：加入 RRF、真实模型、证据引用和错误处理。
4. M3：连接用户端与管理端，完成版本发布和权限闭环。
5. M4—M5：按失败案例推进优化，冻结测试集并完成论文实验。

开始实现前需明确的事实：学校与数据来源、导师是否要求 Spring Boot、设备配置、每周时间、模型 API 可用性、小程序账号与部署条件。它们只影响相应实施步骤，不妨碍现在完成方案。
